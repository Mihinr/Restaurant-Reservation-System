Restaurant Reservation & Table Management System
Part 1: System Design & Architecture
Prepared by: Mihin Ratnayake
Date: January 6, 2026

1. System Overview
The restaurant reservation system is designed to support multiple restaurant locations, manage table availability in real-time, handle walk-ins and waitlists, and coordinate staff for seating assignments. The system is built to handle high concurrency, maintain data consistency, and provide a reliable, scalable experience for both customers and staff.
Key Goals:
•	Real-time table availability and reservation management
•	Prevent double-booking during concurrent requests
•	Provide staff with real-time seating status updates
•	Maintain customer profiles and reservation history
•	Enable reporting on occupancy, revenue, and peak hour performance
Chosen Tech Stack:
•	Language: TypeScript (strict mode)
•	Database: MySQL – chosen for its relational integrity, support for ACID transactions, and scalability with complex queries
•	Backend: Node.js with Express
•	Frontend: React with TypeScript (Vite for build performance)
•	Version Control: Git with feature-branch workflow
•	Containerization: Docker + Docker Compose for service orchestration
Service	Responsibility	Communication
Reservation Service	Handle table searches, bookings, modifications, cancellations, waitlist	REST APIs, asynchronous events for updates
Restaurant Service	Manage restaurant locations, tables, and staff assignments	REST APIs, database queries, event notifications
Customer Service	Manage customer profiles, reservation history
	REST APIs, database queries

1.1 Service Architecture
What services will comprise your system? (minimum 3 services required)

Service Decomposition
The system will be implemented as a microservices architecture with the following core services:
1. User Service
Responsibilities:
•	User authentication and authorization (JWT token generation/validation)
•	Customer profile management (CRUD operations)
•	Customer preferences and history
•	Role-based access control (Customer, Staff, Admin)
Boundaries:
•	Manages all user-related data
•	Handles authentication for all other services
•	Does NOT contain reservation or table data
•	Publishes user events (e.g., "UserCreated", "UserUpdated")
2. Reservation Service
Responsibilities:
•	Reservation lifecycle management (create, read, update, cancel)
•	Availability checking and conflict detection
•	Waitlist management
•	Reservation modifications and business rules enforcement
•	Time-based automatic expiration of pending reservations
Boundaries:
•	Core business logic for reservation operations
•	Owns reservation and waitlist data
•	Consumes table availability events
•	Publishes reservation events for other services
3. Table Management Service
Responsibilities:
•	Restaurant location and table configuration
•	Real-time table status updates (available, occupied, reserved, maintenance)
•	Table capacity and layout management
•	Staff coordination for seating assignments
•	Table search and availability calculation
Boundaries:
•	Owns table and restaurant location data
•	Provides real-time availability
•	Handles concurrent status updates
•	Does NOT manage reservations directly
4. Notification Service (Optional but recommended)
Responsibilities:
•	Email/SMS notifications for reservations
•	Real-time updates via WebSocket
•	Notification templates and scheduling
•	Retry logic for failed notifications
Service Communication Patterns
Synchronous Communication (Request/Response)
•	When: Immediate response required, simple CRUD operations
•	Pattern: REST APIs with HTTP/HTTPS
•	Examples:
o	User login/authentication
o	Reservation creation (with immediate confirmation)
o	Table status queries
Asynchronous Communication (Event-Driven)
•	When: Decoupled operations, eventual consistency acceptable
•	Pattern: Message Queue with RabbitMQ/Kafka
•	Examples:
o	Reservation created → Update analytics
o	Table status changed → Notify frontend clients
o	User registered → Send welcome email

Communication Matrix:
Service	Communication Method	Purpose
Frontend → All Services	HTTP REST	Direct API calls
Reservation → Table Service	Synchronous HTTP	Real-time availability check
Reservation → User Service	Synchronous HTTP	Validate user exists
All Services → Notification	Async (Message Queue)	Send notifications
Table → Reservation	Async (Events)	Table status updates
Reservation → Analytics	Async (Events)	Business intelligence

Service Resilience and Failure Handling
Service Resilience and Failure Handling
Circuit Breaker Pattern
•	Implement circuit breakers for inter-service calls
•	Library: opossum or similar circuit breaker implementation
•	Configuration:
typescript
// Example configuration
circuitBreakerOptions = {
  timeout: 3000, // Timeout after 3 seconds
  errorThresholdPercentage: 50, // Trip after 50% errors
  resetTimeout: 30000, // Reset after 30 seconds
}
Retry Pattern with Exponential Backoff
•	Automatic retries for transient failures
•	Implementation:
typescript
async function callWithRetry(
  serviceCall: () => Promise<any>,
  maxRetries = 3,
  baseDelay = 1000
): Promise<any> {
  let lastError: Error;
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await serviceCall();
    } catch (error) {
      lastError = error;
      if (i < maxRetries - 1) {
        const delay = baseDelay * Math.pow(2, i);
        await new Promise(resolve => setTimeout(resolve, delay));
      }
    }
  }
  throw lastError;
}
Bulkhead Pattern
•	Isolate service failures using connection pools and thread pools
•	Each service has independent database connection pools
•	HTTP clients with connection limits per service
Fallback Strategies
•	Cache Fallback: Return cached data when service is unavailable
•	Default Response: Return safe default values
•	Queue for Later: Queue operations for processing when service recovers

Data Consistency Patterns
Saga Pattern (for distributed transactions)
•	Use Case: Reservation creation involving multiple services
•	Implementation:
typescript
// Saga for creating a reservation
1. Start Reservation Saga
2. Reserve Table (Table Service) → Compensate: Release Table
3. Create Reservation (Reservation Service) → Compensate: Cancel Reservation

Eventual Consistency with Events
•	Services publish events after local transactions
•	Other services consume events and update their local state
•	Example: Reservation created → Analytics service updates metrics
Two-Phase Commit (2PC) Alternative
•	For strong consistency requirements
•	Implementation: Using database transactions across services via XA transactions
•	Trade-off: Higher latency, more complex failure handling
Compensating Transactions
•	For operations that cannot be rolled back
•	Example: Email notification sent → Send follow-up cancellation email

Distributed Transaction Handling
Approach: Orchestrated Saga Pattern
•	Central saga orchestrator manages transaction flow
•	Each service exposes compensating endpoints
•	Sequence for Reservation Creation:
text
1. [Orchestrator] Begin Reservation Transaction
   ↓
2. [Orchestrator] → Table Service: Lock Table (10s timeout)
   ↓
3. [Orchestrator] ← Table Service: Table Locked Successfully
   ↓
4. [Orchestrator] → Reservation Service: Create Reservation
   ↓
5. [Orchestrator] ← Reservation Service: Reservation Created
   ↓
6. [Orchestrator] → Notification Service: Send Confirmation
   ↓
7. [Orchestrator] ← Notification Service: Notification Sent
   ↓
8. [Orchestrator] → All Services: Commit Transaction
Transaction Timeout and Rollback
•	Timeout: 30 seconds for complete reservation flow
•	Automatic Rollback: If any step fails, execute compensating transactions in reverse order
•	Manual Intervention: Failed compensations logged for manual resolution
Idempotency Keys
•	All mutation operations include idempotency keys
•	Prevents duplicate processing of retried requests
•	Implementation:

1.2 Database Design

What database technology will each service use? (PostgreSQL or MySQL)
Choice: MySQL 8.0
Justification:
•	ACID Compliance: Strong transactional guarantees for reservation system
•	Referential Integrity: Foreign key constraints for data consistency
•	Mature Ecosystem: Proven reliability for high-traffic systems
•	JSON Support: Native JSON data type for flexible schema (MySQL 8.0+)
•	Row-Level Locking: InnoDB engine supports concurrent reservations
•	Read Replicas: Built-in support for scaling read operations
•	Cost-Effective: Open-source with strong community support
Alternative Considered: PostgreSQL
•	Why Not Chosen: While PostgreSQL has excellent JSON support and advanced features, MySQL's simpler replication model and widespread expertise in I have made it the better choice for this project's timeline.

-- Core reservations table
CREATE TABLE reservations (
    id VARCHAR(36) PRIMARY KEY DEFAULT (UUID()),
    reservation_number VARCHAR(20) UNIQUE NOT NULL,
    user_id VARCHAR(36) NOT NULL,
    restaurant_id VARCHAR(36) NOT NULL,
    table_id VARCHAR(36),
    
    -- Reservation details
    party_size INT NOT NULL CHECK (party_size > 0),
    reservation_date DATE NOT NULL,
    reservation_time TIME NOT NULL,
    duration_minutes INT NOT NULL DEFAULT 90,
    
    -- Status lifecycle
    status ENUM('pending', 'confirmed', 'seated', 'completed', 'cancelled', 'no_show') DEFAULT 'pending',
    status_updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    -- Customer contact (denormalized from user service)
    customer_name VARCHAR(255),
    customer_phone VARCHAR(20),
    
    -- Business logic
    special_requests TEXT,
    
    -- Optimistic locking
    version INT DEFAULT 1,
    
    -- Timestamps
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    -- Constraints
    CONSTRAINT chk_party_size CHECK (party_size >= 1),
    CONSTRAINT chk_duration CHECK (duration_minutes BETWEEN 30 AND 240),
    
    -- Indexes (comprehensive for all query patterns)
    INDEX idx_user_id (user_id),
    INDEX idx_restaurant_id (restaurant_id),
    INDEX idx_table_id (table_id),
    INDEX idx_status (status),
    INDEX idx_reservation_datetime (reservation_date, reservation_time),
    INDEX idx_restaurant_datetime (restaurant_id, reservation_date, reservation_time),
    INDEX idx_user_restaurant (user_id, restaurant_id),
    UNIQUE INDEX idx_table_timeslot (table_id, reservation_date, reservation_time) 
        WHERE status IN ('pending', 'confirmed', 'seated')
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

Handling Cross-Service Data
Approach: Eventual Consistency with Denormalization
1. Data Duplication Strategy:
•	Reservation Service stores denormalized copies of:
o	Customer name and phone (from User Service)
o	Restaurant details (from Table Service)
•	Purpose: Avoid synchronous calls during critical paths

    email: string;
    firstName: string;
    lastName: string;
    phone: string;

// Reservation Service consumes this event

•	Cache invalidated when Table Service publishes status change events
•	Fallback to synchronous API call if cache miss

How will you handle data that needs to exist across services?
Core Principle: Domain Ownership with Strategic Duplication
The fundamental rule is that each service owns its domain data, but we accept that some data must be duplicated across services for performance and availability reasons. Here's our approach:
________________________________________
1. Data Ownership Strategy
Primary Source of Truth
•	User Service: Owns user profiles, authentication, and authorization data
•	Table Service: Owns restaurant locations, table configurations, and real-time status
•	Reservation Service: Owns reservations, waitlist, and booking lifecycle
What Gets Duplicated and Why:
Customer Information in Reservations
•	Why: Reservation Service needs customer names and contact info for staff reference and notifications
•	What's Duplicated: Customer name and phone number (denormalized from User Service)
•	How: Copied during reservation creation, updated via events
Restaurant Details in Reservations
•	Why: Reservation records should be self-contained for reporting and history
•	What's Duplicated: Restaurant name and basic location info
•	How: Copied during reservation creation
Table Availability Status
•	Why: Reservation Service needs quick availability checks without synchronous calls
•	What's Duplicated: Current table status and capacity
•	How: Cached with short TTL, invalidated on status changes
________________________________________
2. Synchronization Mechanisms
Event-Driven Updates (Primary Method)
When source data changes, the owning service publishes an event. Other services consume these events to update their local copies.
Examples:
•	When a user updates their profile → User Service publishes UserUpdated event → Reservation Service updates customer info in existing reservations
•	When a table status changes → Table Service publishes TableStatusChanged event → Reservation Service updates its availability cache
•	When a restaurant updates hours → Table Service publishes event → Frontend caches are invalidated
Cache-Aside Pattern
For read-heavy data like table availability:
1.	Check local cache first
2.	If cache miss, call source service synchronously
3.	Store result in cache with appropriate TTL
4.	Subscribe to change events to invalidate cache
Read-Through API Gateway
For some cross-service queries, the API Gateway can aggregate data from multiple services, presenting a unified view to the client without requiring data duplication.

3. Consistency Models by Use Case
Strong Consistency Required:
•	Reservation Creation: Must have up-to-date table availability and user validation
•	Payment Processing: Must verify user and reservation status
•	Real-time Seat Assignments: Staff needs accurate current table status
Eventual Consistency Acceptable:
•	Customer Profile Updates: It's okay if reservation history shows old name temporarily
•	Analytics and Reporting: Slightly stale data is acceptable
•	Email Notifications: Can use slightly outdated customer email
________________________________________
4. Data Freshness Strategies
Time-to-Live (TTL) Based:
•	Short TTL (seconds): For table availability and real-time status
•	Medium TTL (minutes): For restaurant details and operating hours
•	Long TTL (hours/days): For static reference data
Event-Driven Invalidation:
Subscribe to change events from source services to immediately invalidate stale data.
Version Numbers:
Include version numbers with duplicated data. When versions mismatch, trigger refresh from source.
________________________________________
5. Handling Missing or Stale Data
Fallback Strategies:
1.	Synchronous Call: If cached data is missing or too stale, make direct API call
2.	Default Values: Use reasonable defaults when data unavailable
3.	Degraded Experience: Show partial information with loading states
Reconciliation Processes:
•	Scheduled Jobs: Nightly jobs to sync mismatched data
•	Manual Triggers: Admin tools to force resync specific records
•	Monitoring: Track data drift between services and alert on anomalies
________________________________________
6. Design Principles for Cross-Service Data
Minimize Duplication
Only duplicate what's absolutely necessary for:
•	Performance (avoiding synchronous calls in hot paths)
•	Resilience (service should function during source service outages)
•	Convenience (self-contained records for common queries)
Clear Ownership
Each piece of data has exactly one owner service. Other services treat it as read-only copy.
Explicit Contracts
Define clear interfaces for what data can be accessed and how it should be synchronized.
Traceability
Maintain metadata about where duplicated data came from and when it was last updated.
________________________________________
7. Failure Scenarios and Recovery
When Source Service is Down:
1.	Continue using cached/stale data if acceptable
2.	Queue operations requiring fresh data for later retry
3.	Provide appropriate user feedback ("system updating")
When Synchronization Fails:
1.	Retry with exponential backoff
2.	Store in dead-letter queue for manual intervention
3.	Log inconsistencies for later reconciliation
Data Corruption:
1.	Validate data integrity on receipt
2.	Discard invalid data and refresh from source
3.	Alert on patterns of corruption

Ensuring Data Consistency in a Distributed System
Core Philosophy: Right Consistency for Right Scenario
We use different consistency strategies based on the business requirement and failure tolerance of each operation.
1. Strong Consistency Patterns
For Critical Operations (Reservation Creation, Updates)
Saga Pattern with Compensation:
•	Each business transaction spans multiple services
•	Local transactions at each service
•	If any step fails, compensating transactions undo previous steps
•	Example: Reservation creation fails → release table lock, clean up reservation record
Two-Phase Commit Alternative:
•	For operations requiring atomicity across services
•	Coordinator service manages prepare/commit phases
•	Used sparingly due to complexity and latency
Optimistic Concurrency Control
•	Version numbers on resources (like reservations)
•	Clients include version in update requests
•	Server rejects updates with stale versions
•	Prevents lost updates in concurrent scenarios
2. Eventual Consistency Patterns
For Non-Critical Data (User Profile Updates, Restaurant Info)
Event-Driven Updates:
•	Source service publishes change events
•	Consumer services update their local copies asynchronously
•	Acceptable delay: seconds to minutes
•	Example: User changes phone number → reservation records updated eventually
Message Queue with Retries:
•	Guaranteed delivery of events
•	Automatic retry on failures
•	Dead-letter queue for manual intervention
3. Concurrency Control for Hot Resources
Preventing Double Bookings
Database-Level Locking:
•	SELECT ... FOR UPDATE on table availability rows
•	Short-lived locks (5-10 seconds)
•	Prevents race conditions for same time slot
Application-Level Reservations:
•	Temporary holds on tables
•	Expire after short period if not confirmed
•	Allows for multi-step reservation flows
4. Idempotency for Reliability
All Mutation Operations
•	Clients provide idempotency keys
•	Server deduplicates duplicate requests
•	Essential for retry safety
•	Prevents duplicate charges, double bookings
5. Consistency Verification and Repair
Monitoring and Reconciliation
Automated Consistency Checks:
•	Scheduled jobs compare data across services
•	Detect and log inconsistencies
•	Example: Compare user name in User Service vs Reservation Service
Repair Mechanisms:
•	Automatic repair for known-safe scenarios
•	Manual intervention for complex inconsistencies
•	Audit logs of all repairs
Data Quality Metrics
•	Track consistency drift rates
•	Alert on abnormal inconsistency levels
•	Dashboards showing data health
6. Failure Handling Strategies
When Services are Unavailable
Circuit Breakers:
•	Fail fast when dependency is down
•	Prevent cascading failures
•	Fallback to cached data when appropriate
Queue and Retry:
•	Queue operations requiring unavailable services
•	Automatic retry when service recovers
•	User receives "processing" status
When Synchronization Fails
Retry with Backoff:
•	Exponential backoff for retries
•	Maximum retry attempts
•	Manual intervention after retries exhausted
Compensating Actions:
•	Reverse completed steps
•	Notify administrators
•	User-friendly error messages
7. Business-Specific Consistency Rules
Reservation System Specifics
Temporal Consistency:
•	Real-time table status for staff
•	Near-real-time for customer apps
•	Eventual for historical reports
Causal Consistency:
•	Reservation creation happens before confirmation email
•	Table status changes before staff notifications
•	Cancellation before refund processing
8. Implementation Guardrails
Development Guidelines
•	Clear documentation of consistency requirements per operation
•	Code reviews verify consistency patterns
•	Testing includes concurrent scenarios
Operational Controls
•	Monitoring for consistency violations
•	Alerting on abnormal patterns
•	Regular consistency audits
9. Trade-offs and Decisions
Consistency vs Availability
•	Strong consistency: For financial transactions and reservations
•	Eventual consistency: For profile updates and non-critical data
•	Choice based on: Business impact, user experience, failure tolerance
Complexity vs Correctness
•	Simpler patterns where eventual consistency suffices
•	More complex patterns (Saga) where correctness is critical
•	Always document the chosen consistency model
10. Continuous Improvement
Learning from Incidents
•	Post-mortems for consistency failures
•	Update patterns based on real-world issues
•	Share learnings across teams
Evolving the System
•	Start with simpler patterns
•	Introduce complexity only when needed
•	Regular review of consistency requirements

Event Types:

•	ReservationCreated (Reservation Service → Notification, Analytics)
•	TableStatusChanged (Table Service → Reservation, Frontend)

2. Integration Events
•	UserUpdated (User Service → Reservation Service for denormalized data)
•	RestaurantHoursChanged (Table Service → Reservation Service)
•	ReservationCancelled (Reservation Service → Table Service)

Caching Strategy for Performance
Multi-Layer Caching Approach:
Layer 1: Client-Side Caching (Browser)
•	What: Static assets, configuration data
•	Duration: 1 hour to 1 day
•	Invalidation: Versioned URLs, cache busting
Layer 2: CDN Caching
•	What: Restaurant images, menu data
•	Duration: 1 day to 1 week
•	Invalidation: Purge API, TTL-based
Layer 3: API Gateway Caching
•	What: Read-heavy, public data (restaurant lists, availability for next hour)
•	Duration: 1 minute to 5 minutes
•	Invalidation: Time-based, event-driven purge
•	Cache-Key: {endpoint}:{params}:{auth-token}
Layer 4: Application-Level Caching (Redis)

Cache-Aside Pattern Example:
typescript
async function getRestaurantAvailability(restaurantId, date, time) {
  const cacheKey = `availability:${restaurantId}:${date}:${time}`;
  
  // 1. Try cache first
  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);
  
  // 2. Cache miss - compute from database
  const availability = await computeAvailability(restaurantId, date, time);
  
  // 3. Store in cache (5 minute TTL)
  await redis.setex(cacheKey, 300, JSON.stringify(availability));
  
  return availability;
}

}

Handling Eventual Consistency
Understanding the Trade-offs:
When Eventual Consistency is Acceptable:
1.	User Profile Updates: Reservation history can show old name briefly
2.	Restaurant Information: Menu changes, description updates
3.	Analytics Data: Reports can be slightly stale
4.	Customer Preferences: Dietary restrictions, favorite tables
When Strong Consistency is Required:
1.	Table Availability: Must be accurate to prevent double booking
2.	Reservation Status: Customer and staff must see same status
3.	Payment Processing: Must have consistent reservation state
4.	Time-sensitive Operations: Waitlist notifications, expiration
Consistency Patterns Implemented:
1. Read-Your-Writes Consistency
•	After creating a reservation, the same user sees immediate confirmation
•	Implemented via: Client-side cache update, sticky sessions, or version checks
2. Causal Consistency
•	If event A happens before event B, all services see them in that order
•	Implemented via: Lamport timestamps, sequence numbers
3. Monotonic Read Consistency
•	Once a user sees a value, they won't see an older value
•	Implemented via: Version vectors, client-side caching
Mitigation Strategies for Eventual Consistency:
1. User Experience Design
•	Optimistic UI Updates: Show change immediately, sync in background
•	Loading States: Indicate when data is synchronizing
•	Last Updated Timestamp: Show users how fresh the data is
•	Manual Refresh Option: Let users force sync if needed
2. Conflict Resolution
typescript
// When User Service and Reservation Service have different user names
function resolveUserNameConflict(localName, remoteName, timestamp) {
  // Use most recent update (last-write-wins with timestamps)
  if (remoteTimestamp > localTimestamp) {
    return remoteName;
  }
  return localName;
}
3. Reconciliation Processes
Scheduled Reconciliation Jobs:
typescript
// Nightly job to sync user data
async function reconcileUserData() {
  const mismatches = await findDataMismatches();
  
  for (const mismatch of mismatches) {
    // Get source truth from User Service
    const sourceData = await userService.getUser(mismatch.userId);
    
    // Update denormalized copies
    await reservationService.updateUserData(mismatch.userId, sourceData);
    
    // Log for auditing
    await auditLog.logReconciliation(mismatch, sourceData);
  }
}

1.5 Data Flow & Business Logic

Customer Searches for Available Tables
Flow Overview:
 
Detailed Steps:
Step 1: Input Validation
•	Customer provides: restaurant, date, time, party size, optional duration
•	Frontend validates: date in future (max 90 days), time during operating hours, party size 1-20
•	Invalid inputs return immediate error
Step 2: Cache Check
•	Check Redis cache for pre-computed availability for this restaurant/time
•	Cache key: availability:{restaurantId}:{date}:{time}:{partySize}
•	Cache TTL: 5 minutes (balances freshness with performance)
Step 3: Database Query
If cache miss, query tables:
•	Find tables at specified restaurant with capacity ≥ party size
•	Tables must be in 'available' or 'reserved' (but check reservation time) status
•	Consider min_party_size if configured for premium tables
Step 4: Conflict Checking
For each candidate table:
•	Check reservations table for conflicts at requested time
•	Consider reservation duration (default 90 minutes)
•	If table is reserved, check if reservation is within ±90 minutes of requested time
•	Exclude tables with conflicting reservations
Step 5: Availability Scoring
Score remaining tables by:
1.	Capacity match: Tables with capacity closest to party size get highest score
2.	Location preference: Window/outdoor tables if customer indicated preference
3.	Recent availability: Tables not recently occupied (for cleaning time)
4.	Staff preference: Tables easy for servers to access
Step 6: Result Processing
•	Sort tables by score (best match first)
•	Limit to top 10 results
•	Calculate next available times if requested time is fully booked
•	Store in cache with 5-minute TTL
•	Return results with metadata (total available, wait time estimate)
Step 7: Real-time Status
•	Availability results include current table status
•	Frontend subscribes to WebSocket for real-time updates
•	If table status changes while customer is viewing, UI updates

Potential Bottlenecks & Solutions
Bottleneck 1: Database Slowdown During Peak Hours
Problem: Too many people booking at 7 PM causes database overload.
Solutions:
1.	Add read replicas - Copy database for read operations only
2.	Use Redis cache - Store popular data in memory
3.	Queue write operations - Process updates in background
4.	Optimize slow queries - Fix inefficient database queries

Problem: Two people try to book same table at same time.

2.	Temporary holds - Reserve table for 2 minutes while booking
3.	Queue system - Process bookings one at a time for hot tables
4.	Smart suggestions - Show alternatives when conflict happens
Bottleneck 3: Real-time Updates Overload
Problem: Too many WebSocket connections for live table status.
Solutions:
1.	Separate WebSocket servers - Don't mix with API servers
2.	Message batching - Send updates in groups, not individually
3.	Connection limits - Max 1000 connections per server
4.	Fallback to polling - Use regular HTTP if WebSocket fails
Bottleneck 4: Cache Overload
Problem: Cache memory fills up, causes slowdowns.
Solutions:
1.	Multi-level cache - Browser → CDN → Redis → Database
2.	Smart expiration - Popular data stays longer, old data removed
3.	Cache warming - Pre-load expected popular data
4.	Monitor hit rates - Track what's working, adjust as needed

Level 2: Application Load Balancer

Level 3: Service Load Balancer
text
Different services → Different server groups
- User service: 2 servers
- Reservation service: 4 servers (needs more power)
- Table service: 4 servers
Benefit: Right resources for each job

Scale DOWN when:
